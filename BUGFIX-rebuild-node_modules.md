# Bug: rebuild rompe backend (login/prom-client) y frontend (vite-plugin-pwa)

Repos: `pwa-app` (NestJS backend + React/Vite frontend). Fecha: 2026-09-17.

## Síntomas

1. Tras `docker compose up -d --build backend`, el contenedor crasheaba al arrancar:

   ```
   TS2307: Cannot find module 'prom-client'
   ```

2. Cuando eso se resolvía, el **login** devolvía 503/504 vía Kong y el proceso de Nest
   **moría en silencio** (sin stack, sin log): el socket de :3000 desaparecía y Kong
   marcaba el target `UNHEALTHY`.

3. El **frontend** en bucle de reinicio (`Restarting (1)`):
   ```
   Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'vite-plugin-pwa'
   imported from /app/vite.config.ts...
   ```

## Causas raíz (2 independientes)

### A) Volumen anónimo stale de `node_modules`

`docker-compose.yml` montaba (backend y frontend):

```yaml
volumes:
  - ./backend:/app
  - /app/node_modules        # ← anonymous volume
```

El volumen anónimo almacena el `/app/node_modules` que tenía **la imagen en el momento
de crear el contenedor** y lo **sombrea** por encima del bind mount. Si el `package.json`
cambia (p. ej. se añade `prom-client` o `vite-plugin-pwa`) y se reconstruye la imagen, el
volumen **viejo** sigue montado y aporta las dependencias **viejas**. Un
`docker compose up -d --build` a secas NO renueva los volúmenes anónimos; solo lo hace
`--renew-anon-volumes`.

### B) Segfault del `bcrypt` del host bajo imagen alpine (musl)

Al quitar el volumen anónimo, el contenedor pasa a usar el `node_modules` del HOST.
En WSL (Ubuntu) ese `node_modules` está compilado para **glibc**. La imagen dev era
`node:20-alpine` (**musl**). Un binario nativo glibc (`.node` de `bcrypt`) bajo musl
**segfaulta** al ejecutar `bcrypt.compare`:

```
node -e "bcrypt.compare(...)"   →   exit_code=139   (SIGSEGV)
```

Síntoma: el login "envenenaba" el proceso (muerte silenciosa, Kong → 503/504).
Un test aislado con `require` + hash de prueba puede dar **falso positivo** (la ruta de
crash solo se dispara con el hash/BCrypt real y coste real). El frontend sufría el mismo
problema de libc con `esbuild` (viene con binario por variante: `@esbuild/linux-x64-musl`).

## Solución definitiva (aplicada)

1. **Eliminar el volumen anónimo de `node_modules`** del compose (backend y frontend):
   los contenedores usan directamente el `node_modules` del host vía el bind mount.

2. **Cambiar el stage `development` de ambos Dockerfiles a `node:20` (Debian/glibc)**
   en lugar de `node:20-alpine` (musl). Así los módulos nativos del host (bcrypt,
   esbuild) cargan y corren sin segfault. Producción sigue en alpine (monta su propio
   `node_modules` dentro de la imagen, sin bind mount).

```yaml
# docker-compose.yml (backend y frontend services)
volumes:
  - ./backend:/app
  - ./frontend:/app     # ya NO hay — /app/node_modules anónimo
```

```dockerfile
# backend/Dockerfile y frontend/Dockerfile (stage development)
FROM node:20 AS development       # Debian/glibc, no alpine
```

Queda el script `dev-rebuild.sh` con el ciclo normal de rebuild + healthcheck:

```bash
./dev-rebuild.sh        # docker compose up -d --build backend + espera /api/health/ready
```

## Verificación

### Backend
- `docker compose up -d --build backend` (varias veces) → sin volúmenes stale.
- Logins reales vía Kong: `superadmin@empresa1.com`, `admin@empresa2.com`,
  `vendedor@empresa3.com` → **login 201 + bootstrap 200** (3/3).
- Proceso `nest` **vivo después del login** (antes moría con 139).
- `GET /api/health/ready` → 200.
- Montajes del contenedor: solo `bind .../backend -> /app` (sin anonymous volume).

### Frontend
- `docker compose up -d --build frontend` → Vite ready (`http://localhost:5173` → 200),
  `RestartCount=0` (antes 100 restarts por `vite-plugin-pwa` no encontrado).

## Regla para el futuro

- **Al añadir/quitar dependencias**: `bun install`/`npm install` en el **host**
  (`backend/`, `frontend/`) y luego el rebuild. Nada de flags de volúmenes.
- **No** volver a `node:20-alpine` en el stage `development` mientras el
  `node_modules` del host (glibc) se monte en el contenedor.
- Si el backend "cae en silencio" tras un login: revisa `exit 139` con
  `docker exec pwa-backend node -e "require('bcrypt').compare(...)"`.
